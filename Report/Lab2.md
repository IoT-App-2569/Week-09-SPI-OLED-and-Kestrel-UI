## 5. คำถามท้ายการทดลองเพื่อการประเมินผล
1. เหตุใดการคำนวณสเกลเซนเซอร์จึงควรทำที่ฝั่ง Kestrel Server แทนที่จะคำนวณบนไมโครคอนโทรลเลอร์ ESP32 ตั้งแต่แรก?
```
เพื่อความยืดหยุ่น และการแยกส่วนรับผิดชอบ ไมโครคอนโทรลเลอร์ มีหน้าที่เพียงแค่อ่านค่าดิบ และส่งขึ้นมา การนำสมการคำนวณมาไว้ที่ฝั่ง Server ทำให้เราสามารถเปลี่ยนสเกล  แก้ไขสมการ หรืออัปเดตระบบได้ทันทีโดย ไม่ต้องไปแฟลชโค้ดใหม่ลงในตัว ESP32 ทุกตัว นอกจากนี้ยังช่วยลดภาระการประมวลผลของอุปกรณ์ IoT ด้วย
```

2. จากการทำ HTTP Forensics หากไม่มีการตรวจสอบเงื่อนไข `RawMax <= RawMin` ในโค้ด จะเกิด Exception ชนิดใดขึ้นในภาษา C# และส่งผลต่อการทำงานของเซิร์ฟเวอร์อย่างไร?
```
ในสมการมีตัวหารคือ (_settings.RawMax - _settings.RawMin) หาก 2 ค่านี้เท่ากัน จะเกิดการ หารด้วยศูนย์ (Divide by Zero)

หากเป็นข้อมูลชนิดเลขจำนวนเต็ม จะเกิด DivideByZeroException ทำให้ Server อาจจะ Crash ได้ถ้าไม่มีการทำ Error Handling

แต่ในโค้ดนี้การคำนวณถูก Cast เป็นชนิด double การหารด้วยศูนย์ใน C# double จะให้ผลลัพธ์เป็น Infinity หรือ NaN  ซึ่งเมื่อถูกส่งออกไปเป็น JSON จะทำให้ระบบฝั่ง Client ที่นำข้อมูลไปใช้ต่อ แปลงค่าไม่ประมวลผลผิดพลาด
```

3. อธิบายสาเหตุทางเทคนิคว่าทำไมคำขอ HTTP POST ที่ไม่มี Header `Content-Type: application/json` จึงถูกปฏิเสธด้วยรหัสสถานะ `415 Unsupported Media Type`?
```
Kestrel Web Server และ Minimal API อาศัยกระบวนการที่เรียกว่า Model Binding ในการแปลงข้อมูลดิบ  ให้เป็น Object ในภาษา C# อัตโนมัติ การที่เราไม่ระบุ Content-Type: application/json เซิร์ฟเวอร์ก็จะไม่รู้เลยว่าข้อมูล Body ที่ส่งมาเป็นฟอร์แมตไหน  ตัว Kestrel จึงปฏิเสธคำขอนั้นทันทีพร้อมแจ้งว่า 415 เพื่อความปลอดภัยและความถูกต้องของข้อมูล
```
