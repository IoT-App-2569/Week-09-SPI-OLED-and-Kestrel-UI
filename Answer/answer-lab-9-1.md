## 2. ผลการทดลองแต่ละกิจกรรม

### กิจกรรมที่ 1.1 — Low-Level SPI & DC Toggle

สร้างท่อส่งสัญญาณ 3 ชั้น คือ `oled_spi_init()` → `oled_send_cmd()` → `oled_send_data()`

หัวใจอยู่ที่การสลับขา DC **ก่อน** เริ่มทรานแซกชัน SPI ทุกครั้ง

| ฟังก์ชัน | ระดับขา DC | ชิปตีความข้อมูลเป็น |
| :--- | :---: | :--- |
| `oled_send_cmd()` | `0` (LOW) | คำสั่งตั้งค่ารีจิสเตอร์ (Opcode) |
| `oled_send_data()` | `1` (HIGH) | ข้อมูลพิกเซลเขียนลง GDDRAM |

**จุดที่ต้องระวังในการตั้งค่าบัส**

* `.miso_io_num = -1` เพราะจอนี้เป็น **Write-Only** ไม่มีขาส่งข้อมูลกลับ
* `.max_transfer_sz = 1024 + 16` ต้องใหญ่พอสำหรับยิง Framebuffer 1KB รวดเดียว ถ้าตั้งน้อยกว่านี้ `oled_flush()` จะ error
* `.mode = 0` คือ CPOL = 0, CPHA = 0 ตรงตามที่ SSD1306 datasheet กำหนด (สุ่มตัวอย่างข้อมูลที่ขอบขาขึ้นของ SCK)
* ใช้ `SPI2_HOST` และให้ไดรเวอร์คุมขา CS เองผ่าน `.spics_io_num` จึงไม่ต้อง `gpio_set_level()` ขา CS ในโค้ดเลย

### กิจกรรมที่ 1.2 — Magic Sequence (Proof-of-Life)

**ผลลัพธ์ที่สังเกตได้:** หน้าจอสว่างขาวทั้งแผ่นทันที

คำสั่งที่ส่งและเหตุผล

| คำสั่ง | ความหมาย | ถ้าไม่ส่งจะเกิดอะไร |
| :---: | :--- | :--- |
| `0xAE` | Display OFF | คอนฟิกรีจิสเตอร์ขณะจอติดอาจเห็นภาพขยะแวบขึ้นมา |
| `0x8D`, `0x14` | **Enable Charge Pump** | **จอมืดสนิท** เพราะไม่มีแรงดัน 7.5V ไปจุดเม็ด OLED |
| `0x20`, `0x00` | Horizontal Addressing | ตัวชี้จะไม่วิ่งข้าม Page อัตโนมัติ ต้องสั่งเปลี่ยน Page เองทุก 128 ไบต์ |
| `0xAF` | Display ON | ชิปประมวลผลอยู่แต่แผงจอไม่เปล่งแสง |

**ข้อพิสูจน์ 3 ข้อจากการที่จอสว่างทั้งแผ่น**

1. บัส SPI สื่อสารได้จริง ไม่ติด error `invalid dev handle`
2. วงจร Charge Pump ภายในชิปทำงาน ยกแรงดัน 3.3V → 7.5V สำเร็จ
3. เม็ดพิกเซลทั้ง 8,192 จุดบนแผงทำงานครบ ไม่มีแถวหรือคอลัมน์ตาย

> **หมายเหตุ:** จอรุ่นที่ใช้เป็นแบบ 2 สี แถบสีเหลือง 16 แถว และแถบสีฟ้า 48 แถว
> เป็นการเคลือบสารเรืองแสงคนละชนิดบนแผง ไม่ใช่สิ่งที่ซอฟต์แวร์สั่งได้

### กิจกรรมที่ 1.3 — Bitwise Canvas บน Framebuffer 1KB

**สูตรแมปพิกัดที่ใช้**

$$\text{byte\_index} = x + \left\lfloor \frac{y}{8} \right\rfloor \times 128
\qquad
\text{bit\_offset} = y \bmod 8$$

**ที่มาของสูตร:** GDDRAM ของ SSD1306 ไม่ได้เรียงเป็นตาราง $x,y$ แบบตรงไปตรงมา แต่แบ่งเป็น **8 Pages** โดย 1 ไบต์ = พิกเซลแนวตั้ง 8 จุดในคอลัมน์เดียวกัน

```
             Col 0   Col 1   Col 2  ...  Col 127
Page 0  →  [byte 0][byte 1][byte 2] ... [byte 127]   ครอบคลุม y = 0..7
Page 1  →  [byte128][byte129]       ...              ครอบคลุม y = 8..15
   :
Page 7  →  [byte896] ...            [byte 1023]      ครอบคลุม y = 56..63
```

ดังนั้น `y / 8` บอกว่าอยู่ Page ไหน (คูณ 128 เพื่อข้ามไปต้น Page นั้น) ส่วน `y % 8` บอกว่าเป็นบิตที่เท่าไรภายในไบต์

**การจุด/ดับพิกเซลแบบไม่กระทบเพื่อนบ้าน**

| การกระทำ | ตัวดำเนินการ | เหตุผล |
| :--- | :--- | :--- |
| จุดพิกเซล | `buf[i] \|= (1 << bit)` | OR เปิดเฉพาะบิตเป้าหมาย บิตอื่นในไบต์ (พิกเซลข้างเคียงอีก 7 จุด) คงเดิม |
| ดับพิกเซล | `buf[i] &= ~(1 << bit)` | AND กับ mask ที่กลับบิต ปิดเฉพาะบิตเป้าหมาย |

ถ้าใช้ `=` แทน `|=` จะเป็นการเขียนทับทั้งไบต์ ทำให้พิกเซลอีก 7 จุดในคอลัมน์เดียวกันดับหมด

**ผลลัพธ์ที่สังเกตได้:** จอขาว 1.5 วินาที → ดับมืด → เหลือจุดสว่าง 4 จุดที่มุมจอพอดี
พิสูจน์ว่า `oled_clear()` ล้างแรมสะอาด และสูตรแมปพิกัดถูกต้องทั้งขอบบน ขอบล่าง ขอบซ้าย และขอบขวา

### กิจกรรมที่ 1.4 — Font Matrix 5x7 และ "Hello World"

ตัวอักษร 1 ตัวใช้ **5 ไบต์** โดยแต่ละไบต์คือ 1 คอลัมน์แนวตั้ง (บิต 0 = แถวบน, บิต 6 = แถวล่าง)
บวกช่องไฟ (Kerning) อีก 1 คอลัมน์ ความกว้างรวมจึงเป็น **6 พิกเซลต่อตัวอักษร**

$$\text{ตัวอักษรต่อบรรทัด} = \frac{128}{6} \approx 21 \text{ ตัว}$$

ข้อความที่แสดง

```c
oled_draw_string(30, 4,  "HELLO WORLD",  true);   // โซนสีเหลือง
oled_draw_string(24, 32, "ID: 67030098", true);   // โซนสีฟ้า
```

### 🔍 คำตอบปริศนานิติวิทยาศาสตร์ — ทำไมภาพถึงกลับหัว?

**ไม่ใช่บั๊กในโค้ดวาดภาพ** — สูตร `oled_draw_pixel()` ถูกต้องทุกประการ ปัญหาอยู่ที่ **ขั้นตอนการสแกนของฮาร์ดแวร์** ซึ่งเกิดหลังจากข้อมูลเข้า GDDRAM ไปแล้ว

ชุด Magic Sequence ในใบงาน 9.1 **จงใจละคำสั่ง 2 ตัวนี้ไว้** จึงตกไปใช้ค่า Reset Default ของชิป

| คำสั่ง | ค่า Default (9.1 ใช้อยู่) | ค่าที่ถูกต้อง | ผลต่อการแสดงผล |
| :--- | :---: | :---: | :--- |
| Segment Re-map | `0xA0` — Col 0 → SEG0 | **`0xA1`** — Col 127 → SEG0 | กลับซ้าย-ขวา (แนวนอน) |
| COM Output Scan Direction | `0xC0` — สแกน COM0 → COM63 | **`0xC8`** — สแกน COM63 → COM0 | กลับบน-ล่าง (แนวตั้ง) |

เมื่อกลับทั้งแนวนอนและแนวตั้งพร้อมกัน ผลลัพธ์คือ **ภาพหมุน 180 องศา** พอดี

**สาเหตุเชิงกายภาพ:** ผู้ผลิตโมดูลติดแผงกระจก OLED กลับด้านกับทิศทางสแกนเริ่มต้นของชิปคอนโทรลเลอร์ เฟิร์มแวร์จึงต้องชดเชยด้วยซอฟต์แวร์เสมอ ซึ่งเป็นเหตุผลที่ไลบรารีสำเร็จรูปทุกตัวใส่ `0xA1` และ `0xC8` ไว้ในลำดับเริ่มต้น

**วิธีแก้ (จะทำในใบงาน 9.4 Case 3):** เพิ่ม 2 บรรทัดนี้ในลำดับเริ่มต้น ก่อนสั่ง `0xAF`

```c
oled_send_cmd(0xA1);  // Segment Re-map : พลิกแนวนอน
oled_send_cmd(0xC8);  // COM Scan Remap : พลิกแนวตั้ง
```

> ตามคำชี้แจงในใบงาน โค้ดที่ส่งในใบงาน 9.1 นี้ **คงสภาพกลับหัวไว้ตามเดิม** เพื่อใช้เป็นหลักฐานเปรียบเทียบในใบงาน 9.4

## 4. ผลการตรวจสอบเชิงนิติวิทยาศาสตร์ (Framebuffer Forensics)

### กิจกรรม 1.1 — Hex Dump Memory Inspection

ฟังก์ชัน `oled_forensic_dump()` ใน [`main.c`](../Code/Lab9-1_OLED_BringUp/main/main.c) ดัมพ์ไบต์ตั้งแต่ index 30 (จุดที่วาดตัว `'H'`) จำนวน 16 ไบต์

ตัว `'H'` ในตารางฟอนต์คือ `{0x7F, 0x08, 0x08, 0x08, 0x7F}` เมื่อวาดที่ `x = 30, y = 4`
ตัวอักษรถูกวาดด้วย offset `y = 4` จึงถูกเลื่อนบิตไป 4 ตำแหน่ง ค่าที่ได้ใน Page 0 คือ `0x7F << 4 = 0xF0` (บิตส่วนที่เกิน 8 จะไปตกอยู่ที่ Page 1)

**ตารางบันทึกผล Hex Dump (Page 0)**

| Byte Index | คอลัมน์ | ค่า Hex | Binary (bit7…bit0) | ตรงกับคอลัมน์ใดของ 'H' |
| :---: | :---: | :---: | :---: | :--- |
| 30 | 30 | `0xF0` | `11110000` | Col 0 — เสาตั้งด้านซ้าย |
| 31 | 31 | `0x80` | `10000000` | Col 1 — คานกลาง |
| 32 | 32 | `0x80` | `10000000` | Col 2 — คานกลาง |
| 33 | 33 | `0x80` | `10000000` | Col 3 — คานกลาง |
| 34 | 34 | `0xF0` | `11110000` | Col 4 — เสาตั้งด้านขวา |
| 35 | 35 | `0x00` | `00000000` | ช่องไฟ (Kerning) |

*(ค่าจริงให้กรอกจาก Serial Monitor ของบอร์ดตนเอง ตัวเลขข้างต้นคือค่าที่คำนวณได้ตามทฤษฎีเมื่อวาดที่ y = 4)*

### กิจกรรม 1.2 — Bit-to-Pixel Forensic Reconstruction

นำบิตมาเรียงใหม่ โดย **บิต 0 อยู่บนสุด** ตามสถาปัตยกรรม Page (อ่านแนวตั้งลงล่าง)

```
        Col0  Col1  Col2  Col3  Col4
        0x7F  0x08  0x08  0x08  0x7F
bit 0 →  ■     .     .     .     ■
bit 1 →  ■     .     .     .     ■
bit 2 →  ■     .     .     .     ■
bit 3 →  ■     ■     ■     ■     ■     ← คานกลางของตัว H
bit 4 →  ■     .     .     .     ■
bit 5 →  ■     .     .     .     ■
bit 6 →  ■     .     .     .     ■
```

**สรุป:** รูปแบบบิต `1` ประกอบกันเป็นเสาตั้ง 2 ข้างและคานกลาง 1 เส้น ตรงกับรูปร่างตัวอักษร `'H'` บนหน้าจอจริงทุกประการ (แม้ภาพบนจอจะกลับหัวจากปัญหา Segment Re-map ก็ตาม — ซึ่งยืนยันอีกชั้นว่าความผิดพลาดไม่ได้อยู่ในแรม)

## 5. คำตอบคำถามท้ายการทดลอง

### ข้อ 1. ทำไมตัวอักษร `'H'` ใช้ข้อมูล 5 ไบต์ และแต่ละไบต์ควบคุมพิกเซลทิศทางใด?

ฟอนต์ที่ใช้เป็นแบบ **5x7** คือกว้าง 5 พิกเซล สูง 7 พิกเซล และจัดเก็บแบบ **Column-Major**

* **5 ไบต์ = 5 คอลัมน์แนวตั้ง** (1 ไบต์ต่อ 1 คอลัมน์)
* แต่ละไบต์ควบคุมพิกเซล **ในแนวตั้ง (แกน Y)** โดยบิต 0 = แถวบนสุด ไล่ลงไปจนบิต 6 = แถวล่างสุด ส่วนบิต 7 ไม่ใช้งาน (เป็น 0 เสมอ)

เหตุผลที่เก็บแบบคอลัมน์ ไม่ใช่แบบแถว: เพราะ **ตรงกับสถาปัตยกรรม GDDRAM ของ SSD1306 พอดี** ซึ่ง 1 ไบต์ในแรมจอก็คือ 8 พิกเซลแนวตั้งเช่นกัน การเก็บฟอนต์แบบเดียวกันทำให้คัดลอกข้อมูลลงบัฟเฟอร์ได้โดยแทบไม่ต้องคำนวณแปลงรูปแบบ ประหยัดเวลา CPU อย่างมาก

### ข้อ 2. ถ้าสลับสาย D0 (SCK) กับ D1 (MOSI) จะเกิดอะไรขึ้น?

**หน้าจอจะไม่ติด (มืดสนิท) และไม่มี Error ใด ๆ แจ้งในโปรแกรม**

เหตุผลเชิงเทคนิค

1. **SPI เป็นบัสแบบทางเดียวที่ไม่มีการตอบรับ (No Acknowledgement)** ต่างจาก I2C ที่ Slave ต้องดึงสาย SDA ลงเพื่อส่ง ACK ฝั่ง ESP32 จึงยิงข้อมูลออกไปได้เรื่อย ๆ โดยไม่มีทางรู้ว่าปลายทางรับได้หรือไม่ ซอฟต์แวร์จะรายงานว่า `ESP_OK` ทุกครั้ง
2. **ชิปจะไม่มีสัญญาณนาฬิกาที่ถูกต้อง** ขา SCK ของ SSD1306 จะไปรับข้อมูลบิตสตรีม (ซึ่งเปลี่ยนสถานะไม่สม่ำเสมอ) ส่วนขาข้อมูลกลับได้รับคลื่นสี่เหลี่ยมของนาฬิกาแทน
3. ชิปจะ latch ข้อมูลที่ขอบขาขึ้นของสิ่งที่มันคิดว่าเป็นนาฬิกา ได้ค่าออกมาเป็นขยะที่ไม่ตรงกับ Opcode ใด ๆ โดยเฉพาะคำสั่ง `0x8D, 0x14` (Charge Pump) และ `0xAF` (Display ON) จะไม่ถูกตีความ วงจรทวีแรงดันจึงไม่เปิด และจอมืดสนิท

**บทเรียนสำคัญ:** อาการ "จอมืดแต่โปรแกรมไม่ error" เป็นลายเซ็นเฉพาะของปัญหาชั้นกายภาพในบัส SPI จึงต้องตรวจสายก่อนเสมอ (เชื่อมโยงกับใบงาน 9.4 Case 1)

### ข้อ 3. ทำไมแก้ไข `s_oled_buffer` แล้วภาพบนจอไม่เปลี่ยนจนกว่าจะเรียก `oled_flush()`?

เพราะระบบนี้ใช้สถาปัตยกรรม **Double Buffering** ซึ่งมีหน่วยความจำอยู่ **2 ชุดแยกจากกันคนละชิป**

| หน่วยความจำ | ตำแหน่ง | บทบาท |
| :--- | :--- | :--- |
| `s_oled_buffer[1024]` | **แรมภายใน ESP32** | Back Buffer — พื้นที่วาดร่าง ผู้ใช้มองไม่เห็น |
| GDDRAM | **ภายในชิป SSD1306** | Front Buffer — เนื้อหาที่แผงจอกำลังสแกนแสดงจริง |

การเรียก `oled_draw_pixel()` เป็นเพียงการแก้ไขบิตในแรมของ **ESP32** เท่านั้น ไม่มีสัญญาณใดวิ่งออกไปบนสาย SPI เลย ทั้งสองชิปเชื่อมกันด้วยสาย SPI เพียง 4 เส้น ไม่ได้แชร์หน่วยความจำกัน ข้อมูลจึงต้องถูก "ขนย้าย" ด้วยคำสั่งอย่างชัดเจน — ซึ่งก็คือ `oled_flush()` ที่ตั้งขอบเขต (`0x21`, `0x22`) แล้วยิงข้อมูล 1,024 ไบต์ข้ามไป

**ข้อดีของการแยกสองชั้นแบบนี้:**

1. **ไม่เกิดภาพฉีก (Screen Tearing / Flicker)** ถ้าวาดลง GDDRAM โดยตรงทีละพิกเซล ผู้ใช้จะเห็นภาพค่อย ๆ ก่อตัวขึ้นทีละจุด และเห็นภาพเก่าผสมภาพใหม่ในเฟรมเดียวกัน แต่วิธีนี้ภาพจะปรากฏครบสมบูรณ์พร้อมกันในครั้งเดียว
2. **ประสิทธิภาพสูงกว่ามาก** การวาดรูปซับซ้อน (เช่น UI 3 โซนพร้อมกรอบและแถบเกจ) อาจแตะพิกเซลเดิมซ้ำหลายรอบ ถ้าส่ง SPI ทุกครั้งที่แตะพิกเซลจะเสียเวลามหาศาล แต่วิธีนี้ยิงข้อมูลออกบัสเพียง **1 ทรานแซกชันต่อ 1 เฟรม**
