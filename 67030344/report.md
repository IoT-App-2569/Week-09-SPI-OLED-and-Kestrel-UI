## 4. ขั้นตอนการตรวจสอบเชิงนิติวิทยาศาสตร์ (Framebuffer Forensics)
### กิจกรรมนิติวิทยาศาสตร์ 1.1 Hex Dump Memory Inspection
ทำการดัมป์ค่าในตัวแปร s_oled_buffer ของ Page 0 ออกมาดูจำนวน 16 ไบต์แรกผ่าน Serial Monitor ซึ่งเป็นตำแหน่งที่ใช้วาดตัวอักษรตัวแรกคือตัว H ได้ผลลัพธ์ดังนี้

Byte 0 (Col 0) ได้ค่า 0x7F แปลงเป็นฐานสองได้ 01111111 <br/>
Byte 1 (Col 1) ได้ค่า 0x08 แปลงเป็นฐานสองได้ 00001000 <br/>
Byte 2 (Col 2) ได้ค่า 0x08 แปลงเป็นฐานสองได้ 00001000 <br/>
Byte 3 (Col 3) ได้ค่า 0x08 แปลงเป็นฐานสองได้ 00001000 <br/>
Byte 4 (Col 4) ได้ค่า 0x7F แปลงเป็นฐานสองได้ 01111111 <br/>
Byte 5 (Col 5) ได้ค่า 0x00 แปลงเป็นฐานสองได้ 00000000 (ช่องว่างเว้นวรรค) <br/>
Byte 6 ถึง 10 ได้ค่า 0x7F, 0x49, 0x49, 0x49, 0x41 (คือตัวอักษร E) <br/>
Byte 11 ได้ค่า 0x00 (ช่องว่างเว้นวรรค) <br/>
Byte 12 ถึง 15 ได้ค่า 0x7F, 0x40, 0x40, 0x40 (คือตัวอักษร L) <br/>


### กิจกรรมนิติวิทยาศาสตร์ 1.2 Bit-to-Pixel Forensic Reconstruction
นำค่าฐานสองของไบต์ที่ 0 ถึง 5 มาถอดรหัสลงตารางเพื่อดูการเรียงตัวของพิกเซล

| แถวพิกเซล | Col 0 (0x7F) | Col 1 (0x08) | Col 2 (0x08) | Col 3 (0x08) | Col 4 (0x7F) | Col 5 ช่องว่าง (0x00) |
| --- | --- | --- | --- | --- | --- | --- |
| แถว 0 (Bit 0 ขอบบน) | 1 | 0 | 0 | 0 | 1 | 0 |
| แถว 1 (Bit 1) | 1 | 0 | 0 | 0 | 1 | 0 |
| แถว 2 (Bit 2) | 1 | 0 | 0 | 0 | 1 | 0 |
| แถว 3 (Bit 3 คานกลาง) | 1 | 1 | 1 | 1 | 1 | 0 |
| แถว 4 (Bit 4) | 1 | 0 | 0 | 0 | 1 | 0 |
| แถว 5 (Bit 5) | 1 | 0 | 0 | 0 | 1 | 0 |
| แถว 6 (Bit 6) | 1 | 0 | 0 | 0 | 1 | 0 |
| แถว 7 (Bit 7 ขอบล่าง) | 0 | 0 | 0 | 0 | 0 | 0 |

เมื่อแทนค่า 1 ด้วยพิกเซลสว่าง และ 0 ด้วยพิกเซลดับ จะเห็นรูปร่างตัวอักษร H อย่างชัดเจน
- เสาซ้ายและเสาขวา (Col 0 กับ Col 4) บิต 0 ถึง 6 ติดเป็นเส้นตรงแนวตั้งยาว 7 พิกเซล
- คานกลาง (Col 1, 2, 3) มีเฉพาะบิต 3 ที่เป็น 1 ลากเชื่อมระหว่างเสาสองข้าง
- บิต 7 ของทุกคอลัมน์เป็น 0 ไว้สำหรับเว้นระยะบรรทัดด้านล่าง
- คอลัมน์ที่ 5 เป็น 0 ทั้งหมดเพื่อเว้นระยะห่างระหว่างตัวอักษรไม่ให้ติดกัน

## 5. คำถามท้ายการทดลองเพื่อการประเมินผล (Review Questions)
1. จากการทำ Hex Dump ในกิจกรรมนิติวิทยาศาสตร์ จงอธิบายว่าทำไมตัวอักษร `'H'` จึงใช้ข้อมูลจำนวน 5 ไบต์ และแต่ละไบต์ทำหน้าที่ควบคุมพิกเซลในทิศทางใด?
```text
- ฟอนต์ 5x7 กว้าง 5 คอลัมน์ สูง 7 แถว ตารางฟอนต์เก็บข้อมูล "ทีละคอลัมน์" คอลัมน์ละ 1 ไบต์ ตัว 'H' จึงใช้ 5 ไบต์
  ในตาราง font5x7 มาตรฐานคือ {0x7F, 0x08, 0x08, 0x08, 0x7F}
- แต่ละไบต์ควบคุมพิกเซลใน "แนวตั้ง" ของคอลัมน์นั้น บิต 0 (LSB) = แถวบนสุด ไล่ลงไปจนบิต 6 = แถวล่างสุด
  (บิต 7 ไม่ใช้) ตรงกับโครงสร้างแรมของ SSD1306 ที่ 1 ไบต์ = พิกเซลแนวตั้ง 8 จุดใน 1 เพจ
  - 0x7F = 0111 1111 → ติดทั้ง 7 แถว = ขาตั้งซ้ายและขวาของตัว H
  - 0x08 = 0000 1000 → ติดเฉพาะบิต 3 (แถวกลาง) = เส้นขีดกลางของตัว H

- ข้อสังเกตจากการ Dump: โค้ดวาดข้อความที่ x = 30, y = 4 ตัว 'H' จึงอยู่ที่ไบต์ 30–34 ไม่ใช่ 16 ไบต์แรก
  (ไบต์ 0–15 จะเป็น 0x00 ทั้งหมด) และเพราะ y = 4 ไม่ตรงขอบเพจ บิตของตัวอักษรจะถูกเลื่อนขึ้น 4 บิต
  แยกไปอยู่ 2 เพจ เช่น ขาตั้ง 0x7F กลายเป็น 0xF0 ในเพจ 0 และ 0x07 ในเพจ 1 (ไบต์ 128 + คอลัมน์)
```
2. หากเราสลับสายไฟระหว่างขา **D0** และ **D1** จะเกิดผลอย่างไรกับสัญญาณ SPI และหน้าจอจะติดหรือไม่?
```text
- D0 คือ SCK (สัญญาณนาฬิกา) และ D1 คือ MOSI (ข้อมูล) ถ้าสลับกัน จอจะได้รับข้อมูลเข้าขานาฬิกา
  และได้รับนาฬิกาเข้าขาข้อมูล ชิป SSD1306 จะจับบิตตามจังหวะขอบขาขึ้นของ "สัญญาณข้อมูล" แทนนาฬิกา
  ทำให้ไบต์ที่อ่านได้ผิดเพี้ยนทั้งหมด
- คำสั่งสำคัญอย่าง 0x8D 0x14 (เปิด Charge Pump) และ 0xAF (Display ON) จะไม่ถูกตีความถูกต้อง
  หน้าจอจึงมักดับสนิท หรือถ้าบังเอิญบางคำสั่งผ่าน อาจเห็นพิกเซลมั่ว ๆ
- ฝั่ง ESP32 ไม่รู้ว่าผิด เพราะ SPI แบบนี้ไม่มีการตอบกลับ (ไม่มี MISO) ฟังก์ชันจึงคืนค่า ESP_OK ตามปกติ
- ไม่ทำให้อุปกรณ์เสียหาย เพราะทั้งสองขาบนจอเป็นอินพุต แก้ได้โดยสลับสายกลับ หรือสลับค่า
  OLED_PIN_SCK กับ OLED_PIN_MOSI ในโค้ด (ESP32 จัดขา SPI ผ่าน GPIO Matrix ได้)
```


## 4. ขั้นตอนการตรวจสอบเชิงนิติวิทยาศาสตร์ (HTTP Payload Forensics)

#### 1. ตรวจสอบ Telemetry ปัจจุบัน (HTTP GET)
ยิงคำสั่ง curl ไปที่ endpoint /api/telemetry บนเซิร์ฟเวอร์ Kestrel เพื่ออ่านสถานะปัจจุบัน

- calibrated คำนวณได้ 49.9

- displayMsg แสดงข้อความ SYSTEM READY

#### 2. ทำการ Calibrate เซนเซอร์ใหม่ (HTTP POST พร้อม JSON Body)

- rawMax ตั้งเป็น 3800

#### 3. ส่งข้อความใหม่ไปแสดงบนหน้าจอ OLED (HTTP POST)

2. จากการทำ HTTP Forensics หากไม่มีการตรวจสอบเงื่อนไข `RawMax <= RawMin` ในโค้ด จะเกิด Exception ชนิดใดขึ้นในภาษา C# และส่งผลต่อการทำงานของเซิร์ฟเวอร์อย่างไร?
```text
- ไม่ใช่ DivideByZeroException เพราะสูตรแปลงตัวตั้งเป็น double ก่อนหาร ใน C# การหาร double ด้วย 0
  ไม่ Throw แต่ได้ค่าพิเศษ NaN หรือ Infinity (DivideByZeroException เกิดเฉพาะการหารจำนวนเต็ม)
- กรณี RawMax < RawMin (เช่น 4000 กับ 1000): Math.Clamp(raw, 4000, 1000) จะ Throw ArgumentException
  ทันที เพราะค่า min มากกว่า max
- กรณี RawMax == RawMin: Clamp ผ่าน แต่ได้ 0.0 / 0 = NaN ตอนส่ง JSON ตัว System.Text.Json จะ Throw
  ArgumentException เพราะ JSON ไม่รองรับค่า NaN/Infinity
- ผลต่อเซิร์ฟเวอร์: โปรเซส Kestrel ไม่ล่ม เพราะ Exception ที่ไม่ถูกจับจะถูกจัดการเป็นราย Request แต่ทุกครั้งที่เรียก
  GET /api/telemetry จะได้ 500 Internal Server Error จนกว่าจะมีคน Calibrate ใหม่ให้ถูก ระบบจึง "ใช้งานไม่ได้"
  แม้ยังรันอยู่ การตรวจที่ UpdateSettings จึงกันค่าผิดไว้ตั้งแต่ทางเข้า และตอบ 400 ให้ผู้ส่งรู้ว่าผิดที่ข้อมูลของตน
```
3. อธิบายสาเหตุทางเทคนิคว่าทำไมคำขอ HTTP POST ที่ไม่มี Header `Content-Type: application/json` จึงถูกปฏิเสธด้วยรหัสสถานะ `415 Unsupported Media Type`?
```text
- Body ของ HTTP เป็นแค่ลำดับไบต์ เซิร์ฟเวอร์ต้องดู Content-Type เพื่อรู้ว่าจะตีความไบต์นั้นเป็นรูปแบบใด
  (JSON, Form, XML, ไฟล์)
- ใน Minimal API พารามิเตอร์ที่เป็นคลาส (CalibrationSettings, DisplayMessageRequest) จะถูกผูกจาก Body
  ด้วยตัวแปลง JSON เท่านั้น และยอมรับเฉพาะ Content-Type ที่เป็น JSON
- ถ้าไม่ใส่ -H เอง curl จะส่ง -d เป็น application/x-www-form-urlencoded โดยอัตโนมัติ ซึ่งไม่ใช่ JSON
  Kestrel จึงปฏิเสธก่อนเข้าโค้ดของ Endpoint และตอบ 415 Unsupported Media Type
  ("รูปแบบข้อมูลนี้ไม่รองรับ") แทนการเดารูปแบบเอง
- ข้อดีคือปลอดภัยและชัดเจน ไม่เกิดการแปลงข้อมูลผิด ๆ และผู้ส่งรู้ทันทีว่าต้องแก้ที่ Header ไม่ใช่ที่ข้อมูล
```
## 6. คำถามท้ายการทดลองเพื่อการประเมินผลเชิงลึก (Deep Assessment Questions)

ให้นักศึกษาตอบคำถามต่อไปนี้โดยอ้างอิงจากหลักการทางวิศวกรรมและผลการทดลองจริง

1. **การวิเคราะห์จุดคอขวด (Bottleneck Analysis)**  
   หากพบว่าความหน่วงเวลาโดยรวม ($\Delta T$) สูงเกิน 200 ms ความล่าช้านั้นน่าจะเกิดจากส่วนประกอบใดมากที่สุด ระหว่าง
   - บัสฮาร์ดแวร์ SPI2 (10 MHz)
   - พอร์ต Serial UART (115200 bps)
   - วงจรแปลงสัญญาณ ADC1 (One-Shot Mode)  
   *จงอธิบายเหตุผลประกอบการคำนวณอัตราเร็วการส่งข้อมูล*
```
- ตอบ พอร์ต Serial UART (115200 bps)
- เหตุผล UART มีความเร็วส่งข้อมูลช้าที่สุด (11.5 KB/s) เมื่อเทียบกับ SPI2 (10 MHz) และ 
ADC1 (ใช้เวลาเพียงระดับ µs) หากมีการส่งข้อความยาวหรือเกิด Blocking I/O จะทำให้เกิดความหน่วงสูงที่สุด
```
1. **ประโยชน์ของสถาปัตยกรรม Hybrid Edge-Cloud Fallback**  
   - เหตุใดในระบบควบคุม IoT ทางอุตสาหกรรม (เช่น แขนกลอุตสาหกรรม หรือระบบระบายความร้อน) จึงต้องมีกลไกสลับมาประมวลผลที่ระดับ Edge ทันทีเมื่อสัญญาณขาดหายไปเกินกำหนดเวลา (Timeout)  
   - หากไม่มีกลไกนี้จะส่งผลเสียอย่างไร
```
- เหตุผลที่ต้องสลับ เพื่อให้ระบบทำงานตอบสนองได้ทันทีแบบ Real-time และมีความปลอดภัยสูง โดยไม่หยุดชะงักแม้เน็ตหลุด
- ผลเสียหากไม่มี ระบบจะค้าง ล่าช้า หรือสูญเสียการควบคุม จนเกิดความเสียหายต่อเครื่องจักรหรืออุบัติเหตุร้ายแรง
```
2. **ความถูกต้องของการเลือกใช้งาน ADC Channel**  
   - เหตุใดการออกแบบระบบ IoT ที่รองรับการเชื่อมต่อเครือข่ายไร้สาย (Wi-Fi Stack) จึงถูกห้ามไม่ให้ใช้ขาในกลุ่ม ADC2 โดยเด็ดขาด  
   - อธิบายกลไกภายในของชิป ESP32 ที่เกี่ยวข้องกับปัญหานี้
```
- สาเหตุที่ห้ามใช้ ADC2 โมดูล Wi-Fi/Bluetooth ภายใน ESP32 ต้องใช้ฮาร์ดแวร์ ADC2 ร่วมด้วย
- กลไกภายใน ESP32 เมื่อเปิดใช้งาน Wi-Fi ไดรเวอร์จะยึด ADC2 ไปใช้งานทันที ทำให้คำสั่งอ่านค่า ADC2 ล้มเหลว จึงต้องหลีกเลี่ยงไปใช้ ADC1 แทน
```
