|:---:|---|:---:|:---:|:---:|:---:|

## 2. บันทึกผลกิจกรรมนิติวิทยาศาสตร์ 3.1: การตรวจวัดความหน่วงเวลาเชิงนิติวิทยาศาสตร์ (End-to-End Latency Forensics)

### 2.1 ผลการบันทึกเวลาในระบบ (Timeline Log Tracing)

- **T₀ (จังหวะหมุน Potentiometer / อ่านค่า ADC สดบน ESP32):** `1700000000000 ms`
- **T₁ (Kestrel Web Server รับ HTTP/JSON Payload จาก ESP32):** `1700000000025 ms`
  - ΔT_network = 25 ms
- **T₂ (ESP32 รับคำสั่งตอบกลับและสั่ง OLED Flush หน้าจอเสร็จสิ้น):** `1700000000042 ms`
  - ΔT_display = 17 ms

### 2.2 การคำนวณความหน่วงรวมของระบบ (End-to-End Latency)

สูตรการคำนวณ

\[
\Delta T = T_2 - T_0
\]

แทนค่า

\[
\Delta T = 1700000000042 - 1700000000000
\]

\[
\boxed{\Delta T = 42\text{ ms}}
\]

### 2.3 การวิเคราะห์และประเมินผลมาตรฐาน Real-time

จากการวัดความหน่วงรวม (ΔT) ได้ค่า **42 ms** ซึ่งต่ำกว่าเกณฑ์มาตรฐาน 100 ms สำหรับการตอบสนองแบบ Real-time ทางกายภาพ ระบบจึงมีความลื่นไหลสูง ผู้ใช้งานไม่รู้สึกถึงความล่าช้า (Lag) ขณะหมุนปรับค่าเซนเซอร์

## 3. คำตอบคำถามท้ายการทดลองเพื่อการประเมินผล (Review Questions)

### ข้อ 1: หากการแสดงผลบนหน้าจอ OLED มีความล่าช้า (Lag) กว่าหน้าเว็บอย่างเห็นได้ชัด ความล่าช้านั้นน่าจะเกิดจากจุดคอขวด (Bottleneck) ใดในระบบ?

**คำตอบ**

ความล่าช้าอาจเกิดจากจุดคอขวดหลักดังต่อไปนี้

1. **คอขวดที่การส่งถ่ายข้อมูลสู่หน้าจอ (Display Transfer Bottleneck):** การเรียกใช้ฟังก์ชันวาดพิกเซลและ Flush บัฟเฟอร์ขนาด 1KB สู่ GRAM บนชิป SSD1306 บ่อยเกินไป หรือใช้ความถี่สัญญาณนาฬิกาบนบัสต่ำเกินไป

2. **คอขวดจากการบล็อกการทำงานใน Task (Blocking Task / Delay):** มีการใช้ฟังก์ชันหน่วงเวลาประเภท Blocking เช่น `vTaskDelay()` หรือ `delay()` ใน Loop การประมวลผลหลัก ทำให้กระบวนการอ่านค่าและส่งข้อมูลขัดจังหวะกันเอง

3. **คอขวดระดับเครือข่ายและการรอคอย HTTP Response (HTTP Transaction Overhead):** ESP32 ต้องรอคอยผลตอบกลับ (Blocking I/O) จาก Kestrel Web Server นานเกินไปก่อนที่จะไปอัปเดตหน้าจอ OLED

### ข้อ 2: เหตุใดการใช้บัส SPI 10 MHz จึงช่วยลดความหน่วงเวลาในการอัปเดตหน้าจอ OLED ได้ดีกว่าการใช้บัส I2C 100 kHz ในระบบ Closed-Loop เช่นนี้?

**คำตอบ**

1. **ความเร็วในการส่งถ่ายข้อมูลสูงกว่ามาก (Significantly Higher Bandwidth):** บัส SPI ที่ความถี่ 10 MHz มีความเร็วในการส่งข้อมูลมากกว่าบัส I2C ที่ความถี่ Standard 100 kHz ถึง **100 เท่า** (10 Mbps เทียบกับ 100 kbps)

2. **เวลาในการส่ง Framebuffer สั้นกว่า:**
   - บนบัส I2C 100 kHz จะใช้เวลาส่งข้อมูลประมาณ **80–100 ms** ต่อเฟรม
   - บนบัส SPI 10 MHz จะใช้เวลาส่งข้อมูลเพียงประมาณ **1 ms** ต่อเฟรม

   โดยใช้ข้อมูล Framebuffer ขนาด 1KB (8,192 บิต)

3. **ลด Overhead ของโปรโตคอล:** บัส I2C ต้องมีบิต ACK/NACK และการจ่าหน้า Device Address ทุก ๆ ไบต์ ในขณะที่ SPI ใช้สายสัญญาณ Chip Select (CS) และ Data/Command (DC) ควบคุมโดยตรง ทำให้ไม่เสียเวลาจัดการ Protocol Header ช่วยให้การอัปเดตจอภาพแบบ Real-time Closed-Loop มีความหน่วงต่ำที่สุด

## 4. สรุปผลการทดลอง

จากการทดลองได้ตรวจสอบความสอดคล้องของข้อมูลระหว่าง ESP32 จอแสดงผล OLED และ Web SVG Dashboard โดยทดสอบการหมุน Potentiometer ทั้งหมด 5 ตำแหน่ง พบว่าค่า Raw ADC และค่าร้อยละที่แสดงบน OLED และ Web Dashboard ตรงกันทุกจุดทดสอบ

นอกจากนี้ยังได้ศึกษาการตรวจวัดความหน่วงเวลาแบบ End-to-End จากข้อมูล Timeline Log พบว่าระบบมีความหน่วงรวม 42 ms ซึ่งต่ำกว่าเกณฑ์ 100 ms ตามที่กำหนดในการทดลอง ทำให้เข้าใจการประเมินประสิทธิภาพของระบบ IoT แบบ Real-time รวมถึงจุดคอขวดที่อาจส่งผลต่อความเร็วในการแสดงผล
